# 💡 어르신 일자리 알림 (가칭)

> 작성일: 2026-08-28 · 상태: 기획 확정, 착수 전

## 한 줄 요약

스마트폰이 익숙하지 않은 **전국 70대 어르신**에게 **내가 사는 시군구의 노인 일자리**를 큰 글씨 카드 한 장씩 보여주고 **전화 한 번으로 문의**까지 연결하는 안드로이드·iOS 앱. 성공하면 **월 활성 사용자의 15%가 전화 버튼을 누른다**.

---

## 문제 / 타겟 사용자

### 발단

기획자의 어머님(70세, 경기 김포 거주, **카카오톡만 사용**)이 **"복지관에서 뭘 하는지 몰라서 못 가신다"**. 정보가 없어서가 아니라 정보에 닿는 경로가 없다.

### 확장된 문제

타겟을 전국으로 넓히면 문제는 이렇게 재정의된다:

> **어르신은 "내 동네에 어떤 일자리·활동이 있는지" 알 방법이 사실상 없다.** 정보는 공공 시스템에 다 있지만, 거기까지 가는 길이 어르신의 디지털 역량 밖에 있다.

### 근거

| 근거 | 수치 | 출처 |
|---|---|---|
| 앱을 써도 **스스로 설치를 못 한다** | 65~79세 505명 중 87.1%가 앱 사용, 그중 **63.2%가 설치·삭제 불가** | 분당서울대병원 김광일 교수팀 (2022, 한국의학회지) |
| 스마트폰은 있지만 활용이 막힌다 | 노인 스마트폰 보유율 **76.6%** (2020년 56.4%→2023년), 그러나 **67.2%가 "정보화 사회 적응 어려움"** | 2023 노인실태조사 (보건복지부, 65세↑ 10,078명) |
| 기존 공공앱은 실패했다 | 복지부 28개 앱에 **약 120억 원** 투입. '오늘건강' 월 이용자 **72명**, '아이사랑' 평점 **1.1/5.0**, 복지로 앱 **2.8/5.0** | 투데이e코노믹 |
| 제공자조차 앱을 주 경로로 안 본다 | 노인일자리여기 공식 안내가 "온라인이 어려우면 **전화(1544-3388)나 복지관 직접 방문**" 병기 | 정부24 |
| 민간 시니어앱도 설치와 실사용이 따로 논다 | '시놀' 누적 다운로드 3만 vs **MAU 7,000** (23%) | 브라보마이라이프 |

### 주 사용자 (구체적으로 한 명)

**70세 여성, 경기 김포 거주, 카카오톡만 사용, 앱 설치는 자녀가 대신 해줌.**
어머님은 타겟 사용자이자 **첫 번째 검증 대상**이다. 어머님이 안 쓰시면 전국 확장은 의미가 없다.

> 🔶 **가정**: 어머님과 비슷한 어르신도 "일자리"에 관심이 있다 — 원래 확인한 니즈는 복지관 행사였고, 일자리 니즈는 아직 직접 확인하지 못했다. **검증 필요.**

## 목표 & 성공 지표

| 구분 | 지표 | 현재 | 목표 | 측정 시점 |
|---|---|---|---|---|
| **핵심** | 월 활성 사용자 중 **전화 버튼 탭 비율** | 0% (미출시) | **15%** | 출시 후 3개월 |
| 보조 | 주 1회 이상 재방문율 | 0% | 23% 이상 (시놀 벤치마크 초과) | 출시 후 3개월 |
| 보조 | 어머님 개인 사용: 월 앱 열람 횟수 | 0회 | 4회 이상 (주 1회) | 출시 후 1개월 |
| **가드레일** | 앱 실행 후 **첫 화면 도달 실패율**(크래시·무한로딩) | — | **1% 미만** | 상시 |
| **가드레일** | 위치 권한 **거부율** | — | **30% 미만** (거부해도 앱은 동작해야 함) | 출시 후 1개월 |

**왜 전화 탭인가**: 노인 일자리의 실제 신청 절차가 "담당자에게 전화"다. Senuri 상세 API에 담당자 연락처가 들어 있어 데이터가 곧바로 행동으로 이어진다. 어르신에게 전화는 가장 익숙한 행동이고, 앱이 자동으로 측정할 수 있는 유일한 신호이자 실제 전환 지점이다.

> 🔵 **오픈 질문**: 15%라는 목표치에 벤치마크가 없다. 출시 후 첫 달 실측값을 기준선으로 재설정할 것.

## MVP 범위

### 포함

| 기능 | 어떤 문제를 푸는가 |
|---|---|
| **내 지역 노인 일자리 목록** (카드 1장씩) | "내 동네에 뭐가 있는지 모른다" |
| **전화 걸기 버튼** | "알아도 어떻게 신청하는지 모른다" — 핵심 전환 지점 |
| **GPS 자동 지역 판정** | 시/도 17개 × 시군구 250개를 어르신이 고르게 하지 않는다 |
| **설정에서 지역 변경** | GPS 오판(경계·실내) 복구 + 자녀가 대신 설정 |
| **주 1회 푸시 알림** | 설치형 앱의 최대 약점(앱을 안 엶)을 완화 |
| **글자 크기 조절** | 노안 대응. OS 설정을 따르되 앱 안에서도 조절 |
| **앱 사용법 안내** | 어르신이 헤매실 때 돌아올 곳 + 자녀가 설명할 때 |

### 제외 — 그리고 왜

| 제외 항목 | 이유 | 나중에? |
|---|---|---|
| **복지관 행사 정보** | 전국 API가 없다(아래 데이터 조사 참조). 800곳을 하나씩 크롤링하기엔 1단계 규모를 넘어선다 | ✅ **2단계 필수 항목** |
| 워크넷 채용정보 | 인증키 발급에 **기업회원 가입 + 담당자 심사** 필요, 개인 불가. 연령 필터도 없음 | 조건 충족 시 |
| 길찾기 연동 | 지도 앱 조작이 또 다른 벽. 전화로 물어보는 편이 어르신에겐 쉬움 | 3단계 |
| 회원가입·로그인 | 63.2%가 설치도 못 하는데 로그인은 확실한 이탈 지점 | ❌ 영구 제외 |
| 지원서 작성·온라인 신청 | 실제 절차가 전화·방문이라 앱으로 대체 불가 | ❌ |
| iOS 스토어 출시 | Flutter로 코드베이스는 확보하되, 1차 검증은 어머님 폰(Android) | 2단계 |

## 노안 대응 UI/UX 설계 기준 ★

> 이 섹션은 협상 대상이 아니다. 모든 화면·컴포넌트가 아래 수치를 만족해야 한다.

### 왜 일반 접근성 기준으로는 부족한가

WCAG AA의 명도 대비 4.5:1은 **20/40 시력** 기준으로 산정됐고, W3C 원문은 *"20/40 is commonly reported as typical visual acuity of elders at roughly **age 80**"*이라고 서술한다. 즉 **80세 전후가 AA의 경계선**이다. 70대가 타겟이면 규격 논리상 **AAA(7:1)를 기본값으로** 삼아야 한다.

### 정량 기준 (구현 시 그대로 적용)

| 항목 | 적용값 | 근거 |
|---|---|---|
| **본문** | **18–20sp** | 고령층 친화 표준 14pt(≈18.7px) + Material Body Large 16sp 상향 |
| **제목** | **24sp 이상** | Material Headline Small |
| **캡션 최소** | **16sp** | — |
| **주요 버튼** | **최소 64dp** (≈12mm) | KS X 3253 §6.5 "9mm 이상" + 고령자 연구 19.05mm |
| **비가역 동작 버튼** | **72dp 이상** | 동일 |
| **버튼 간 간격** | **12–16dp** | Android 8dp 하한 + 고령자 연구 6.35mm |
| **명도 대비** | **7:1** (WCAG AAA) | 20/80 시력 보상치. 4.5:1은 80세 경계선 |
| **행간** | **글자 크기의 1.5배** | WCAG 2.2 SC 1.4.12 |
| **자간** | 글자 크기의 0.12배 이상 | 동일 |
| **폰트 웨이트** | **400(Regular)–500(Medium)** | Thin/Light 금지 — 획이 얇으면 배경에 묻힌다 (Penn State) |

### 노안의 실제 영향 → 설계 함의

| 사실 | 수치 | 설계 함의 |
|---|---|---|
| 대비 감도 저하 | **80세는 20세보다 80% 낮음** | 7:1 대비 필수, 회색 텍스트 금지 |
| 필요 광량 | **60세는 20세보다 3배** | 밝은 배경 기본, 다크모드는 선택지로만 |
| 색 인지 | **청색·녹색을 구분하기 어렵고, 진한 청색과 검정은 아예 구분 못 함** | **색 + 아이콘 + 텍스트로 세 번 겹쳐 표시**. 색만으로 의미 전달 금지 |
| 손 떨림 | KS X 3253 부속서가 컨트롤 크기를 정한 근거로 명시 | 64dp 이상, 간격 확보 |
| 시각 손실 유병률 | 65–74세 16%, 75–84세 19% | 스크린리더(TalkBack) 대응 필수 |

### 금지 목록 (근거 포함)

| 금지 | 근거 |
|---|---|
| **더블탭·롱프레스·드래그·회전 제스처** | 61~92세 100명 연구: 오류와 소요 시간이 크게 늘고, 드래그는 아예 끝내지 못함 → **탭 한 번으로 모든 기능에 닿게** |
| **아이콘 전용 버튼** | NN/g: 텍스트 라벨 필수, 호버 없이도 **항상 보이게** |
| **자동으로 사라지는 토스트/스낵바** | Material 기본 4초로는 부족. WCAG 2.2.1은 20초 전에 알리라고 한다 → `LENGTH_INDEFINITE` + 닫기 버튼 |
| **얇은 폰트(100–300)** | 획이 배경에 묻혀 대비 기준에 못 미침 |
| **저대비 회색 텍스트** | KS X 3253 부속서가 "저시력·노인 사용 곤란" 사례로 명시 |
| **깜빡임** | KWCAG 6.3.1: 초당 3~50회 금지 |
| **시간 제한** | KWCAG 6.2.1: 최소 20초 사전 고지 및 연장 가능 |

### 글자 최소화 원칙

"글자를 줄인다"와 "정보를 뺀다"는 다르다. 해법은 **한 화면에 한 가지, 나머지는 눌러서 보기**다.

- 홈 카드: **직무명 + 장소 + 전화 버튼**만 (급여·시간은 상세에서)
- 날짜는 "8월 30일 (토)" — **요일 병기**
- 시간은 "오전 10시" — **24시제 금지**
- 긴 직무명은 자르지 말고 **줄바꿈** (`...` 생략 금지)
- 전문용어 금지: "공고" → "모집", "접수" → "신청"

## 기술 접근

### 스택 (Flutter 3.47.2 / Dart 3.13.2 기준)

```yaml
dependencies:
  http: ^1.6.0                # GitHub raw JSON
  url_launcher: ^6.3.2        # tel: 스킴
  path_provider: ^2.1.6       # 로컬 캐시
  geolocator: ^14.0.3         # GPS (COARSE)
  firebase_core: ^4.14.0
  firebase_messaging: ^16.6.0 # 주 1회 푸시
```

**상태관리 패키지 없음** — `FutureBuilder` + `setState`로 충분.
- Riverpod이 푸는 문제(전역 상태 공유, 복잡한 의존성)가 이 앱엔 없다
- `provider`는 Flutter 공식 문서에서 추천 목록에서 빠졌다
- 나중에 필요해져도 `fetchJobs()`를 `FutureProvider`로 감싸면 그걸로 끝이다

**탈락시킨 대안**
| 대안 | 탈락 사유 |
|---|---|
| `flutter_local_notifications` | `notification` 페이로드면 OS가 알아서 띄운다. 쓸 이유 없음 |
| `hive` | 2022년 이후 방치된 상태 |

### 아키텍처

```
┌─────────────────────────────────────────┐
│  GitHub Actions (private repo, 일 1회)   │
│  ┌───────────────────────────────────┐  │
│  │ ① Senuri API 전량 페이징 수집(XML) │  │
│  │ ② 주소 → 법정동코드 정규화         │  │
│  │ ③ 시군구별 분류                    │  │
│  │ ④ jobs/{시군구코드}.json 커밋      │  │
│  │ ⑤ FCM HTTP v1 토픽 푸시 (주 1회)   │  │
│  └───────────────────────────────────┘  │
└──────────────────┬──────────────────────┘
                   │ GitHub raw (ETag 304)
                   ▼
┌─────────────────────────────────────────┐
│  Flutter App                             │
│  GPS → 오프라인 폴리곤 → 시군구코드      │
│      → 해당 JSON 다운로드 → 파일 캐시    │
│      → 카드 표시 → 전화                  │
└─────────────────────────────────────────┘
```

**왜 서버가 없는가**: 사용자 데이터를 저장하지 않는 읽기 전용이라 정적 JSON이면 충분하다. 서버비 0원, 유지보수도 거의 없다.

### GPS → 시군구 판정

| 항목 | 결정 | 이유 |
|---|---|---|
| 코드 체계 | **법정동코드로 통일** | 통계청 SGIS와 섞으면 조인 실패 |
| 경계 데이터 | **오프라인 폴리곤 내장** (`vuski/admdongkor`) | `sggcd`가 법정동 5자리와 일치. 네트워크·API 키 불필요 |
| 위치 정확도 | **COARSE** (2km 격자) | 시군구 판정에 충분. 권한 요청 부담 최소화 |
| 주소 정규화 | juso.go.kr API로 **매핑 테이블을 한 번 만들어 커밋** | rate limit 5초/10건, 승인키가 IP 단위라 Actions에서 계속 호출하기엔 맞지 않는다 |
| 인접 지역 | 사전 정의 테이블 (13KB) | 경계 거주자 대응 |

### ⚠️ 반드시 처리해야 할 함정

#### 1. 전남광주통합특별시 (최우선)

> **2026-07-01 「전남광주통합특별시」 출범** (법률 제21446호, 2026-03-05 공포)
> 법정동코드에서 **기존 광주(29)·전남(46) 계열이 전부 폐지**되고 **12**로 시작하는 신규 코드로 대체됐다. 폐지 코드 5,067건.

**Senuri API는 당분간 "광주광역시"를 계속 내려줄 가능성이 높다.** 그러면 조인이 **에러 없이 조용히 실패**하고, **광주·전남 일자리가 통째로 빠진다.** 폐지 코드에 옛 명칭 이력이 남아 있으니 **구↔신 별칭 테이블**을 반드시 만들 것.

#### 2. 세종 특례

주소엔 시군구가 없지만(`세종특별자치시 조치원읍`) **코드는 `36110`으로 있다**. "시군구 null" 특례로 처리하면 조인이 깨진다. **문자열 파싱 단계와 코드 매핑 단계를 분리**하고, 세종은 문자열에 시군구가 없어도 `36110`으로 고정 매핑한다.

#### 3. 일반구 비대칭

법정동코드엔 모시(`수원시 41110`)가 **있고**, 경계 데이터엔 **없다**(구 결합형 39개만 존재).
→ **내부 키는 구 단위 5자리(`41117`)로 통일**, 표시만 "수원시"로 접기. 어르신에겐 "수원시 영통구"보다 "수원시"가 친숙하다.

#### 4. 기타 구현 함정

| 함정 | 대응 |
|---|---|
| **GitHub Actions 공개 저장소 60일 무활동 시 자동 비활성화** | **private 저장소** + `workflow_dispatch` 병행 |
| 레거시 FCM(`/fcm/send`) 완전 제거(404 실측) | 서비스 계정 OAuth2 + **HTTP v1 토픽 전송** |
| targetSdk 32 이하는 백그라운드 첫 푸시 소실 | **targetSdk 33+** |
| `res.body`를 쓰면 **한글이 깨진다** | `utf8.decode(res.bodyBytes)` |
| `url_launcher` 6.3.2가 minSdk 24를 요구 | `minSdkVersion 24` |
| `tel:`에서 하이픈·공백 인코딩이 어긋남 | `Uri(scheme:'tel', path:phone)` — `Uri.parse` 금지 |
| `canLaunchUrl`로 먼저 걸러내기 | README가 대놓고 경고한다 — 쓰지 말 것 |
| Android 14 비선형 스케일링 | **sp를 padding·높이 계산에 쓰지 말 것** ("4sp+20sp≠24sp") |
| `textScaleFactor` deprecated | `MediaQuery.textScalerOf(context)` + `withClampedTextScaling(min:1.0, max:2.0)` |
| `korea_administrative_addresses` 패키지 | 마지막 업데이트가 8개월 전 — **통합·화성 4구가 빠져 있을 수 있다**. 경계 데이터에서 직접 만드는 편이 낫다 |
| `geocoder-kr` | **비상업용 라이선스** — 사용 금지 |

## 와이어프레임 설계 프롬프트 (Claude Design)

### 사용법

1. 아래 **공통 제약 블록**을 매 프롬프트 앞에 그대로 붙인다
2. 화면별 프롬프트를 이어 붙여 실행한다
3. 결과를 **검수 체크리스트**로 확인한다

### 공통 제약 블록 (모든 화면에 필수)

```
70대 노안 어르신을 위한 모바일 앱 화면을 디자인해줘.
사용자는 스마트폰이 익숙하지 않고, 카카오톡만 쓰는 수준이야.

[절대 지켜야 할 수치]
- 본문 글자: 18~20sp (제목 24sp 이상, 캡션도 16sp 이상)
- 모든 버튼: 최소 64dp 높이 (비가역 동작은 72dp)
- 버튼 간 간격: 최소 12~16dp
- 명도 대비: 7:1 이상 (WCAG AAA) — 4.5:1로는 부족함
- 행간: 글자 크기의 1.5배
- 폰트 웨이트: 400~500만 사용 (Thin/Light 절대 금지)

[절대 하면 안 되는 것]
- 스와이프/롱프레스/더블탭/드래그로만 도달하는 기능 (탭만으로 전부 되어야 함)
- 아이콘만 있는 버튼 (반드시 글자 라벨 병기)
- 회색 저대비 텍스트
- 자동으로 사라지는 토스트/스낵바
- 색으로만 의미 구분 (색+아이콘+글자 3중으로)
- 청색과 녹색을 나란히 배치 (노안은 구분 못 함)
- 진한 청색을 검정 배경에 사용

[톤]
- 밝은 배경 기본 (60세는 20세보다 3배 밝기가 필요함)
- 글자는 최소한으로. 한 화면에 한 가지 정보만
- 전문용어 금지: "공고"→"모집", "접수"→"신청"
- 날짜는 "8월 30일 (토)" 요일 병기, 시간은 "오전 10시" (24시제 금지)
```

## 로드맵

### 2단계 — 전국 복지관 행사 위치 기반 제공 ★ 필수

> **원래 어머님의 문제가 바로 이거였다.** 1단계에서 미뤘을 뿐, 포기한 게 아니다.

**목표**: 전국 복지관의 행사·프로그램 일정을 수집해, 어르신이 자기 동네 복지관에서 이번 주에 뭘 하는지 볼 수 있게 한다.

#### 실측 조사 결과 (n=192, 서울 169 + 부산 23 전수 조사)

전국 복지관 홈페이지 CMS 분포:

| CMS | 비율 | 대응 방법 |
|---|---|---|
| CUSTOM (자체) | **34.4%** | 기관별 개별 파서 |
| **GNUBOARD** | **26.0%** | ✅ **파서 1개로 커버** |
| **BLOCKED (403)** | **13.5%** | ❌ 포기 대상 |
| COREIFRAME | 13.0% | ✅ 동일 벤더, 파서 1개 |
| 접속불가/빈껍데기 | 7.8% | — |
| WordPress/XE/Rhymix | 5.2% | 개별 |

> ⚠️ **김포 표본(4곳 중 3곳=75% gnuboard)을 전국으로 일반화하면 안 된다.** 실제는 26.0% (95% CI 19.8~32.2%).

#### 단계적 커버리지 전략

```
2-1. 모집단 확정          ← 가장 먼저. "800곳"은 미검증 숫자
2-2. gnuboard 파서 1개    → 26% 커버
2-3. COREIFRAME 파서 1개  → 누적 39%
2-4. CUSTOM 대도시 선별   → 누적 50%+ 목표
2-5. BLOCKED 13.5%는 제외 (설계상 포기)

     ※ 수집 불가 총합 = BLOCKED 13.5% + 접속불가/빈껍데기 7.8% = 21.3%
       → 이론적 최대 커버리지는 약 78.7%
```

#### 확인된 제약

| 제약 | 내용 |
|---|---|
| **행사일은 목록에 없다** | 목록엔 작성일(08-24)만, 실제 행사일(2026.09.07)은 **상세 본문에만** → 요청량 **15배** |
| 봇 차단 13.5% | Rhymix reCAPTCHA로 막혀 있다. **헤더를 위조해도 안 뚫린다**. 한국사회복지관협회 본체도 같은 방식이라 회원목록을 못 가져온다 |
| 자체 CMS 파라미터 | `?state=`, `?idx=`, `?act=`, `?schM=`가 제각각이다. 대덕노인종합복지관은 `?zipEncode=5jxzSX...` **암호화 파라미터**라 URL을 조립하는 것 자체가 불가능 |
| 지자체 포털 대안 실패 | 서울복지포털은 **시설 검색만** 되고, 행사·프로그램 키워드는 **0건** |
| 이미지 벽 | 일부 기관은 시간표가 **JPG**(김포 노인종합복지관 확인) → OCR 필요 |

#### 목록 확보 경로

**협회보다 지자체 포털이 실용적**이다. 서울복지포털에서 169곳, 부산시 페이지에서 23곳을 실제로 추출했다.

#### 법적 검토

> ⚠️ **정정**: 저작권법 제35조의5는 "정보분석(TDM) 예외"가 **아니라 일반 공정이용 조항**이다. 한국에는 **시행 중인 TDM 면책규정이 없다.** 크롤링 근거를 TDM 예외에서 찾는 설계는 성립하지 않으니, 공정이용 법리로 판단해야 한다.

- 판례: 잡코리아-사람인(DB권 침해, 4.5억 배상) vs 야놀자-여기어때(형사 무죄) — **둘 다 영리 경쟁사업자끼리 DB를 무단 이용한 사건**이라, 비영리 복지관 공지 수집과는 사실관계가 다르다
- robots.txt: 확인한 곳은 모두 허용
- **원칙**: robots.txt 준수, 요청 간격 확보, 출처 명시, 원문 링크 제공

#### 비용

800곳 기준 목록+상세 수집 **24.5분** (동시 10, 지연 1초). public 저장소는 Actions 무제한.

#### 깨짐 감지

**전체 합계가 아니라 기관별 기준선** 대비로 감시할 것. 26%짜리 파서가 죽어도 전체 합계로는 티가 안 난다.
→ 기관별 최근 7일 이동평균 대비 **0건이 2회 연속이면 알림**.

#### 1단계에서 미리 준비할 것

2단계를 나중에 얹을 수 있도록 1단계 아키텍처를 이렇게 설계한다:

- 카드 UI를 "일자리 전용"이 아니라 **"지역 기반 항목"** 공통 컴포넌트로 만든다
- JSON 스키마에 `type` 필드를 미리 넣어 `job`과 `event`를 구분할 수 있게 한다
- GPS 지역 판정 로직을 데이터 소스와 분리
- **김포 4곳 크롤러 설계는 폐기하지 않고 보관** (2단계 파일럿으로 재사용)

### 3단계 이후

- 길찾기 연동
- 복지 제도 안내 (복지로 API — 기초연금 등)

## 자체 점검

### 가장 약한 부분

**"어머님이 이 앱을 열 것인가"** — 제품 전체가 이 한 가정 위에 서 있는데, 근거는 정반대를 가리킨다. 63.2%가 앱을 스스로 설치하지 못하고, 복지부는 120억 원을 들여 실패했으며, 노인일자리여기조차 "전화나 방문"을 병기한다. 설치형 앱은 **근거가 뒷받침해서가 아니라 그냥 결정으로 고른 것이다.**

두 번째로 약한 곳은 **일자리와 어머님 니즈가 어긋난다는 점**이다. 확인한 문제는 복지관 행사였는데 MVP는 일자리다. 문제가 있는 쪽이 아니라 데이터가 있는 쪽을 골랐다.

### 반드시 검증할 가정 3개

| 가정 | 틀리면 | 검증 방법 |
|---|---|---|
| 🔶 **어머님이 일자리 정보를 원하신다** | MVP 전체가 헛일이 된다 | **지금 당장 여쭤보기.** 코드 한 줄 쓰기 전에 |
| 🔶 **김포에 일자리가 충분히 있다** | 빈 화면만 보여주는 앱이 된다 | 구현 1단계에서 API 실측 (반나절) |
| 🔶 **어머님이 앱을 여신다** | 설치형 전제가 무너진다 → 카톡 전환 | 출시 후 1개월 열람 횟수. **0회면 플랜 B 발동** |

### 다음 한 걸음

> **어머님께 전화해서 두 가지를 여쭙는다.**
> ① "복지관 말고, 어르신 일자리 정보가 있으면 보시겠어요?"
> ② "지금 폰에 앱 하나 깔아드리면 가끔 열어보실 수 있으세요?"
>
> 이 두 답에 따라 MVP 범위가 바뀌거나, 앱이 아니라 카톡이 정답일 수 있다.
> **개발은 그다음이다.**
